# Модель работы с Codex CLI на цикле final-dev4

**Версия:** `CODEX-WORKING-MODEL v1.0.0`

**Дата:** `2026-09-06`

**Статус:** `ДЕЙСТВУЕТ ДЛЯ final-dev4`

## Зачем этот документ

Реализацию версии `final-dev4` выполняет Codex CLI на машине владельца по
техническому заданию, которое подготовлено и проверено в облачной сессии
Claude. Документ фиксирует, кто что делает, в каких ветках, как задание
попадает к Codex, как проверяется результат и как он публикуется. Всё, что
здесь не описано, решается по `AGENTS.md`, `docs/RESUME.md` и заданию
`docs/tasks/2026-09-06-final-dev4-spec.md`.

## Роли

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| Владелец | Alex | Запускает Codex CLI с промптом из карточки этапа; отвечает на открытые вопросы в анкете; запускает деплой `final-dev4` в GitHub Actions; вливает PR | Не правит код руками параллельно с Codex в той же ветке |
| Исполнитель | Codex CLI (сильнейшая доступная модель, уровень рассуждений — из карточки этапа) | Читает `AGENTS.md` → `docs/RESUME.md` → карточку этапа; реализует этап целиком; гоняет гейты; коммитит, пушит, открывает draft PR с отчётом | Не трогает `final-dev3`, production, frozen source, открытые вопросы без умолчания; не запускает wrangler; не меняет тексты владельца |
| Архитектор и приёмка | Claude (облачная сессия) | Готовит и обновляет ТЗ и карточки; после push Codex делает независимую проверку: diff против реестра решений, прогон гейтов в облаке, live readback после деплоя; ведёт документацию и память; вызывает `@codex review` в PR | Не деплоит (нет ключей и прав `actions: write`); не переписывает работу Codex молча — замечания идут в PR |
| Ревьюер PR | бот `chatgpt-codex-connector` | Отвечает на `@codex review` в PR: находит дефекты в diff | Не выполняет задачи из комментариев (для этого нужна Codex Cloud environment, её нет) |

## Ветки и PR

```
main ──────────────────────────────────────────────────────────────▶
  └─ codex/final-dev4 (PR #11, только docs: ТЗ, разбор, анкета, рекомендации)
       ├─ codex/final-dev4-s1-prep      → PR → main
       ├─ codex/final-dev4-s2-texts     → PR → main   (от main после слияния s1)
       ├─ codex/final-dev4-s3-contacts  → PR → main
       ├─ codex/final-dev4-s4-hours     → PR → main
       ├─ codex/final-dev4-s5-facts     → PR → main
       ├─ codex/final-dev4-s6-services  → PR → main
       ├─ codex/final-dev4-s7-fonts-photos-spacing → PR → main (после ответов владельца)
       └─ codex/final-dev4-s8-release   → отчёт, RESUME, CHANGELOG
```

Правила:

1. **Один этап — одна ветка — один PR.** Имя `codex/final-dev4-s<N>-<slug>` из
   карточки этапа. Маленькие PR проходят `@codex review` и приёмку быстрее, и
   откат одного этапа не ломает остальные.
2. **База.** Первая ветка (`s1-prep`) создаётся от `codex/final-dev4`, чтобы ТЗ
   и карточки были в дереве. После слияния PR #11 в `main` все следующие ветки
   создаются от `main`, каждая после слияния предыдущей: этапы зависят друг от
   друга (маркеры версий, контракт, alias).
3. **PR всегда draft** до зелёного CI и отчёта; цель PR — `main`. Тело по
   `.github/PULL_REQUEST_TEMPLATE.md` плюс proof-блок из карточки.
4. **Никаких прямых push в `main`.** Сливает владелец после приёмки.
5. **Идентификаторы моделей** в коммитах и PR не пишутся.

## Как задание попадает к Codex

1. Карточки этапов лежат в `docs/tasks/codex/2026-09-06-final-dev4-stage-<N>.md`.
   Каждая содержит: цель, применённые решения владельца, пункты разбора, что не
   в скоупе, шаги с файлами и проверками, гейты, приёмку, версии, состав
   отчёта, уровень рассуждений и готовый промпт.
2. Владелец открывает терминал в корне репозитория на нужной ветке и запускает
   Codex CLI, вставляя блок «Промпт для Codex» из карточки. Модель — самая
   сильная доступная; уровень рассуждений — из карточки (`medium` для
   механических правок, `high` для контрактов, скриптов и поведения, `max` для
   перестройки интерфейса).
3. Codex читает по порядку: `AGENTS.md`, `docs/RESUME.md`, этот документ,
   карточку этапа, затем указанные в ней разделы ТЗ и разбора. Тексты берёт
   только из колонки «Правка» `docs/CONTENT-OWNER-REVISIONS-2026-09-06.md`.
4. Если в ходе этапа выясняется, что решения не хватает (карточка молчит, а
   выбор влияет на результат), Codex **останавливается на этом пункте**,
   делает остальное, и пишет вопрос в отчёт PR. Догадки вместо решения владельца
   запрещены.

## Цикл одного этапа

```
карточка → Codex: реализация + гейты + commit + push + draft PR + отчёт
        → CI (npm run check) зелёный
        → Claude: независимая проверка (diff vs реестр решений, гейты в облаке,
          сборка build/variants/final-dev4, скриншоты 1440/390), замечания в PR
        → владелец в PR: «@codex review» → замечания бота
        → Codex: правки по замечаниям (тот же PR) → повторная проверка
        → владелец: Actions → Deploy Previews → Run workflow →
          «Use workflow from» = ветка этапа, only = final-dev4
        → Claude: live readback final-dev4 + байтовый readback final-dev3 и production
        → владелец: слияние PR → следующий этап
```

Деплой из ветки этапа возможен потому, что workflow `Deploy Previews`
делает checkout выбранной в форме ветки; файл workflow при этом должен
существовать в `main` (он там есть). Поле `only` **никогда** не оставлять
пустым: пустое значение публикует все одиннадцать alias, в том числе
`final-dev3`, который должен оставаться эталоном байт в байт.

## Приёмка этапа (Definition of Done)

Этап принят, когда в PR есть:

1. хэш коммита и подтверждение push;
2. diff-доказательство: какие файлы и что именно изменилось;
3. вывод гейтов: `verify-client-copy`, `verify-client-previews`,
   `verify-lead-hook`, unit-тесты, `build-review-numbered`, для этапов с
   версткой — `qa-browser-matrix`;
4. после деплоя — `verify-live-previews.py --only final-dev4` PASS и байтовое
   сравнение `final-dev3` и production «до/после» (SHA-256 не изменился);
5. явное разделение «Проверено / Не проверено / Вопросы владельцу»;
6. обновлённые документы: версии контрактов, `FINAL-QA-CHECKLIST.md`,
   `ERRORS.md` при разобранном дефекте, `RESUME.md` на этапе 8.

«Написано сделано» без пунктов 1–4 = не сделано.

## Открытые вопросы во время реализации

Ответы владельца приходят через интерактивную анкету (ссылка в
`docs/tasks/2026-09-06-final-dev4-questions.md`) или чат. Claude переносит
ответ в «Реестр решений владельца» в ТЗ (новая версия spec) и, если нужно,
обновляет карточку этапа; только после этого Codex берёт пункт в работу.
Пункты «по умолчанию» (кремовое поле 32/20, короткая золотая линия,
«Защита при угрозах» последней, одна строка тем, стрелки снаружи / в шапке,
упор, только колонка «Связь», отступы 80/48 и запас 80) можно делать сразу и
переделать при другом ответе.

## Что запрещено на любом этапе

- Публиковать production (`deploy-pages.ps1`, `--branch=main`) и запускать
  workflow с пустым `only`.
- Менять `docs/sources/client-copy-short-v1.0.0.txt`, редактировать тексты
  владельца, «улучшать» формулировки.
- Пересобирать и публиковать `final-dev3`.
- Править файлы в `build/` руками.
- Отправлять реальный лид в Albato.
- Ставить внешние пакеты, шрифты и иконки вне описанных builder-ов.
