# Ошибки проекта и как их не повторить

**Версия:** `1.3.0`

**Обновлено:** `2026-08-17`

Журнал дефектов, которые уже случились на этом проекте. Каждый — с
причиной, способом проверки и правилом на будущее. Читать перед началом
работы; при появлении нового дефекта дописывать сюда.

---

## 2026-08-13 · Внутренний клип карточки прошёл общий overflow-gate

**Как выглядело.** В карточке `2.10` слово «прецедента» выходило за правую
границу `.fact-card__head` и обрезалось `overflow: hidden` самой карточки.
При этом ширина страницы оставалась корректной, поэтому прежняя матрица
`177/177` не обнаружила дефект.

**Настоящая причина.** Горизонтальная строка `Создание + прецедента` была
рассчитана на короткий unit. Проверка измеряла только
`documentElement.scrollWidth`, а не внутренние clipping-контейнеры.

**Что сделано.** Карточка получила устойчивую вертикальную композицию на
desktop и mobile. Runner `1.4.0` теперь проверяет `scrollWidth/clientWidth`
карточки и её head, а также DOMRect всех потомков и текстовых range; на
`360/390` измеряются оба состояния аккордеона.

**Правило.** Общий page-overflow не доказывает отсутствие локального клипа.
Каждый контейнер с `overflow: hidden` и динамическим текстом должен иметь
отдельный внутренний геометрический gate.

## 2026-08-13 · Stateless `scrollY` нарушил первый downscroll `final-dev3`

**Как выглядело.** В Action Bar `2.3.3` панель и demo-switch появлялись после
минимального смещения от верха (`scrollY > 1`), хотя `.hero__phone` ещё был в
Hero и не прошёл верх viewport. Последовательность `0 → 2 → 50 → 100 → 320`
ошибочно становилась visible до фактического прохода Hero.

**Настоящая причина.** Scoped-условие `return window.scrollY > 1` не хранило
факт геометрического прохода `.hero__phone`. Оно смешало два разных события:
«пользователь ушёл с точного верха» и «Hero-контакт уже пройден».

**Что сделано.** В Action Bar `2.3.4` добавлен scoped boolean latch
`finalDev3HeroPassed`. Он armed-ится только при
`!isIntersecting && rect.top < 0`, сохраняется при возврате внутрь Hero и
сбрасывается при `scrollY <= 1`. Form/menu/focus guards и единый visibility
owner сохранены.

**Regression gate.** `0 → 2 → 50 → 100 → 320` — hidden → pass Hero — visible
→ возврат на `320` — visible → `0` — hidden/reset → повторный `320` — hidden.
Проверяются вместе bar/demo и отсутствие их геометрического overlap.

**Правило.** Если поведение зависит от уже случившегося геометрического
события, одного текущего `scrollY` недостаточно: факт события хранится явно и
имеет отдельный reset-condition.

## 2026-08-13 · Nominal `360px` не покрыл classic-scrollbar effective width

**Как выглядело.** `v2-lora-inter` и `v3-literata-manrope` считались
проверенными на `360×600/668`, но в среде с classic scrollbar `15px`
effective/client layout width составляла `345px` при nominal viewport `360px`.
В V2 Lora H1 занимал `5` строк вместо `4`, а в V3 Manrope-lede — `4` вместо
`3`; CTA обоих вариантов уходили ниже bottom-safe. Этих случаев не было в
прежней матрице `173/173`.

**Настоящая причина.** Runner проверял только nominal viewport и не имел
отдельных effective-width cells. Поэтому успешный `360px` прогон не доказывал
композицию при client/effective layout width `345px`.

**Что сделано.** Browser runner `1.3.2` добавляет для обоих вариантов ячейки
`345×600` и `345×668`: четыре effective-width cells. В
`FONT-VARIANT-V2-MOBILE v1.1.0 | 2026-08-13` Lora H1 получает только
variant-only ширину `+12px`; в `FONT-VARIANT-V3-MOBILE v1.0.0 | 2026-08-13`
такую же минимальную поправку получает Manrope-lede. Дизайн,
семейства/размеры шрифтов, crop и межблочные отступы не меняются. Полная
арифметика становится
`177/177 = 110 main + 55 breakpoint + 8 large + 4 effective-width`.
Полный повторный прогон подтверждён: `177/177 PASS`; ручной visual QA
репрезентативных экранов также пройден.

**Правило.** Для коротких экранов с критичными переносами проверять не только
nominal device width, но и effective layout width при classic scrollbar.
Добавленная cell должна быть variant-specific, если дефект специфичен варианту.

## 2026-08-13 · Нижняя панель исчезала при подъёме обратно к Hero в `final-dev3`

**Как выглядело.** На mobile пользователь прокручивал страницу вниз — нижняя
панель и demo-switch появлялись. При возврате вверх к Hero они исчезали ещё до
верхней точки страницы.

**Настоящая причина.** Это не перекрытие demo-switch: у него `z-index: 41`, у
панели `40`, а их зоны не пересекаются. Общий Action Bar считал Hero пройденным
только пока `.hero__phone` вне viewport. Как только контакт снова появлялся,
он одним `setHidden()` скрывал и панель, и переключатель.

**Историческая попытка исправления.** В `2.3.3` единственный владелец видимости
получил scoped-условие `scrollY > 1`. Оно удержало панель при возврате вверх, но
независимый Claude review обнаружил новый stateless regression: панель стала
показываться до первого прохода Hero. Поэтому прежние `173/173` и manual PASS
для текущего кандидата — `HISTORICAL / INVALIDATED`; действующее исправление
`2.3.4` описано записью выше.

**Правило.** Не лечить такой случай CSS/z-index или вторым контроллером в
Hero. Сначала проверить, какая логика меняет оба элемента; исправлять её в
единственном owner и ограничивать variant-классом.

## 2026-08-11 · PowerShell property expression стала именем Preview-ветки

**Как выглядело.** Batch передал Wrangler аргумент `--branch=$i.b`, где `$i`
был hashtable. PowerShell подставил строковое представление объекта, и
Cloudflare создал ветку `System.Collections.Hashtable.b` вместо трёх ожидаемых
slug.

**Почему static gate не помог.** Локальная карта и build были корректны; ошибка
возникла только при формировании CLI-аргумента. Wrangler успешно задеплоил и
вернул alias, поэтому один exit code недостаточен.

**Что сделано.** Выполнение остановлено; три точных deployment ID удалены через
Cloudflare API, API подтвердил отсутствие ошибочной ветки, alias вернул 404.
Все команды повторены с буквальным `--branch=<slug>`; затем через API сверены
branch, commit и alias каждого из десяти deployment.

**Правило.** В PowerShell не использовать property expression внутри CLI token.
Сначала присвоить scalar (`$branch = [string]$item.branch`) либо передать
буквальный аргумент. После каждого Pages deploy проверять не только exit code,
но и `deployment_trigger.metadata.branch`, commit hash и stable alias.

## 2026-08-04 · Шрифт был разный на каждом устройстве

**Как выглядело.** Владелец: «на разных участках разные шрифты». Внутри
одной строки «Более 30 лет практики» слова выглядели одним шрифтом, а
цифры — другим. На разных устройствах страница выглядела по-разному.

**Что было объявлено.** Три семейства, все скачаны с Google Fonts и
лежали локально:

```css
--font-body:   "Archivo", Helvetica, Arial, sans-serif;
--font-narrow: "Archivo Narrow", "Archivo", sans-serif;
--font-serif:  "Playfair Display", Georgia, serif;
```

**Настоящая причина.** У Archivo и Archivo Narrow **нет кириллического
набора** — только `latin`, `latin-ext` и `vietnamese`. Сайт целиком на
русском. Браузер не может отрисовать кириллицу объявленным шрифтом и
молча берёт следующий в стеке — то есть системный.

Ошибки при этом нет нигде: файлы существуют, `@font-face` грузится со
статусом `loaded`, консоль чистая, `font-display: swap` ничего не
сигналит. С точки зрения браузера всё исправно — просто в шрифте нет
нужных глифов.

**Замер до исправления** (реальный рендер, не объявления):

| Чем рисуется | Глифов | Доля |
|---|---|---|
| Liberation Sans (системный фолбэк) | 6452 | **76.9%** |
| Archivo SemiBold | 1195 | 14.2% |
| Playfair Display Medium | 648 | 7.7% |
| Archivo Narrow SemiBold | 94 | 1.1% |

Три четверти страницы рисовались не тем шрифтом, который выбрал дизайнер.

**Почему это выглядело именно как «разные шрифты на разных участках»:**

1. **Системный шрифт зависит от устройства.** Arial на Windows,
   Helvetica на macOS, Roboto на Android, Liberation Sans на Linux.
   Одна и та же страница выглядит по-разному у клиента и у исполнителя —
   и ни у кого не так, как в макете.
2. **Два шрифта внутри одной строки.** Цифры, латиница и пунктуация
   попадают в диапазон `U+0000-00FF`, который в шрифте есть, а
   кириллица — нет. «Более **24** лет» рисовалось двумя шрифтами:
   слова системным, число — Archivo. То же с «Email», «WhatsApp»,
   телефонными номерами.
3. **Насыщенности схлопывались.** CSS запрашивал веса 400/500/600/700/800,
   у системного фолбэка есть только regular и bold: 500 → regular,
   600/700/800 → bold. Задуманная градация исчезала.

**Как исправлено.** Archivo → **Onest** (кириллица родная, переменный
400–800 закрывает все запрошенные веса без синтеза). Archivo Narrow
убран совсем: узкое начертание в русском тексте всё равно никогда не
отрисовывалось, надстрочники держатся на весе и трекинге. Осталось два
семейства вместо четырёх.

**Замер после:** Onest 92.3%, Playfair Display 7.7%, системного фолбэка
**0%**.

### Правила на будущее

1. **Проверять покрытие набора ДО того, как шрифт попал в макет.**
   Google Fonts CSS API возвращает подмножества комментариями:

   ```bash
   UA="Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 \
   (KHTML, like Gecko) Chrome/120.0 Safari/537.36"
   curl -sS -A "$UA" \
     "https://fonts.googleapis.com/css2?family=Archivo&display=swap" \
     | grep -o "/\* [a-z-]* \*/"
   # /* vietnamese */ /* latin-ext */ /* latin */   <- кириллицы нет
   ```

2. **Осторожно с ложноотрицательным результатом.** Для непеременных
   шрифтов запрос с диапазоном весов (`:wght@400..700`) возвращает
   HTTP 400 и пустой ответ — его легко принять за «кириллицы нет». Для
   таких шрифтов запрашивать без диапазона. На этом я сам ошибся,
   записав PT Sans Narrow и Fira Sans Condensed в «без кириллицы»; при
   повторной проверке кириллица у обоих нашлась.

3. **Проверять факт, а не объявления.** `getComputedStyle` показывает
   запрошенный стек — по нему проблема не видна вообще. Реально
   использованные шрифты отдаёт CDP:

   ```js
   const cdp = await page.context().newCDPSession(page);
   await cdp.send('DOM.enable');
   await cdp.send('CSS.enable');
   const { root } = await cdp.send('DOM.getDocument', { depth: -1 });
   const { nodeIds } = await cdp.send('DOM.querySelectorAll',
     { nodeId: root.nodeId, selector: 'body *' });
   for (const nodeId of nodeIds) {
     const { fonts } = await cdp.send('CSS.getPlatformFontsForNode', { nodeId });
     // [{ familyName: 'Liberation Sans', glyphCount: 750, isCustomFont: false }]
   }
   ```

   **Признак дефекта:** в выдаче есть семейство, которого нет ни в одном
   `@font-face`. Значит браузер добирал глифы из системы.

4. **Сверять запрошенные веса с объявленными.** Если CSS просит вес,
   которого нет в `@font-face`, браузер синтезирует начертание — оно
   отличается от настоящего.

5. **Проверять смешанные строки.** «Email», «WhatsApp», телефоны, числа
   внутри русского текста — там разрыв виден раньше всего.

**Проверено:** ответы Google Fonts CSS API + прямой замер рендера
(8389 глифов). Подробный разбор с источниками —
`insights/2026-08-04-webfont-missing-cyrillic-silent-fallback.md` в
репозитории ADFIX OS.

## 2026-08-04 · Портрет обрезался «до одной головы»

**Как выглядело.** Владелец: «что это только за голова?» В карточке
адвоката от портрета Александра оставалась голова без плеч, рядом Юлия
была снята по пояс — читалось как две разные съёмки.

**Причина.** Окно карточки имело фиксированную альбомную высоту
(`height: clamp(320px, 34vw, 440px)`), а источник — вертикальный портрет.
При `object-fit: cover` вертикальный кадр в альбомном окне обрезается по
горизонтали в районе головы. Плюс сам файл был вторичным кропом
1100×1152 вместо исходника.

**Исправлено.** Окно `4:5` + `height: auto` (пропорция совпадает с
источником — cover ничего не режет). Портрет пересобран из исходника
2794×4284 и приведён к геометрии карточки Юлии.

### Правило

Окно фотографии задавать через `aspect-ratio`, совпадающий с пропорцией
источника, и `height: auto`. Фиксированная высота + `cover` = скрытая
обрезка, которая проявится на неожиданной ширине.

## 2026-08-04 · Срез макушек в hero на широких экранах

**Как выглядело.** На 1920 у Александра обрезана верхняя часть головы.
На 1440, где велась разработка, дефекта не было.

**Причина.** Кадр (1.437) шире hero-бокса, при `cover` он масштабируется
по ширине — и чем шире вьюпорт, тем больше вертикальный излишек, который
обрезается. На 1440 излишек 246px и `object-position: 50% 88%` срезал
только фон, на 1920 излишек вырос до ~535px и те же 88% увели окно до
макушек.

**Исправлено.** Вертикаль 88% → 56%, для 2000+ отдельный шаг 44%.

### Правило

`object-position` в процентах — не абсолютная позиция, а доля от
обрезаемого излишка, и излишек меняется вместе с шириной вьюпорта.
Любой фон-кадр с лицами проверять минимум на **1440 / 1920 / 2560**, а не
только на рабочем разрешении.

## 2026-08-04 · `<picture>` закрыт тегом `</figure>`

**Как выглядело.** На мобильном текст в карточке прецедента выезжал за
левую границу карточки, золотая полоса слева была не видна.

**Причина.** 11 из 12 тегов `<picture>` в документе закрывались
`</figure>`, при том что `<figure>` не открывался нигде. Парсер
отбрасывает чужой закрывающий тег, `<picture>` остаётся открытым, и
следующие блоки становятся его детьми. А для `.precedent-card > picture`
задано `position: absolute; inset: 0` — абсолютные отступы считаются от
padding-box, поэтому падинг карточки 28px переставал работать.

### Правило

Валидность разметки проверять счётчиком парных тегов, а не глазами:

```bash
python3 -c "s=open('index.html').read(); \
print('<picture>', s.count('<picture>'), '</picture>', s.count('</picture>'))"
```

Симптом «CSS не применяется, хотя правило есть» — сначала проверять
структуру документа, а не правило.

## 2026-08-04 · Правка «для мобильного», сделанная для всех версий

**Как выглядело.** Владелец попросил убрать дубль WhatsApp из телефонной
строки на мобильном. Я удалил текст из разметки — то есть на всех
версиях сразу, включая десктоп, где дубля не было видно как проблема.
Плюс это был **утверждённый клиентом текст**.

### Правила

1. Замечание про конкретный брейкпоинт исправлять **в media query**, а не
   в разметке. Прятать через CSS, текст в HTML сохранять.
2. Утверждённый текст не удалять и не переформулировать без явного
   подтверждения владельца.
3. После правки, которая должна была задеть один брейкпоинт, доказывать
   это попиксельным сравнением остальных:

   ```python
   from PIL import Image, ImageChops
   bbox = ImageChops.difference(before, after).getbbox()
   # None => не изменилось
   ```

## 2026-08-04 · Пошёл разворачивать заново вместо существующей площадки

**Как выглядело.** Владелец попросил задеплоить онлайн для проверки на
устройстве. Я начал искать, куда развернуть: проверил Vercel (проектов
нет), потом стал поднимать GitHub Pages отдельным workflow. Владелец
остановил: площадка уже существует — **https://gambarian-landing.pages.dev/**,
Cloudflare Pages, разворачивали ранее.

**Что я сделал не так.** Начал решать задачу с нуля, не спросив и не
проверив, куда проект уже публикуется. Признаки были прямо в коде — в
`site/index.html` лежит комментарий «Временная площадка на pages.dev»,
и его я прочитал ещё в начале сессии. То есть данные были, а я их не
связал: искал новый хостинг вместо того, чтобы найти существующий.

**Почему это дорого.** Лишний хостинг — это второй адрес того же сайта,
расхождение версий и путаница у клиента. Плюс потраченное время на
Vercel и черновой workflow, который пришлось удалить.

### Правила

1. Перед развёртыванием — **сначала найти, куда проект уже публикуется**:
   комментарии в разметке, `docs/`, `wrangler.toml`/`vercel.json`,
   workflow в `.github/`, история сессий. Новую площадку заводить только
   если существующей нет.
2. Если развёртывание уже где-то живёт — обновлять его, а не плодить
   параллельное.
3. Признаки существующего деплоя стоит фиксировать в `docs/` в момент,
   когда они впервые встретились, а не полагаться на память сессии.
   **Сделано:** `docs/DEPLOY.md` — адрес площадки, что публикуется,
   команда обновления и порядок проверки.

**Состояние на 2026-08-04.** Живая площадка отдаёт **старую** версию:
там нет ни новых шрифтов, ни переработанного hero, ни карточек-аккордеонов.
Обновить её из этой сессии нечем: папки `site/` в ветке `main` нет (то
есть Cloudflare питается не из этого репозитория), MCP-инструменты
Cloudflare в сессии только на чтение (D1/KV/R2/Workers — ни одного метода
публикации), а `wrangler` не авторизован (`wrangler whoami` →
«You are not authenticated»). Нужен либо токен Cloudflare API с правом
`Cloudflare Pages: Edit`, либо развёртывание руками владельцем.

## 2026-08-04 · Ещё раз про артефакт: тёмная страница на светлом фоне

**Как выглядело.** Одностраничная сборка публикуется как artifact. Фон
задавался только на `:root`. Обёртка смотрелки выставляет собственный
светлый фон **на `body`**, и он перекрывал правило: страница выходила
«светлое на светлом», текст читался с трудом.

**Правило.** Для artifact фон и цвет текста задавать и на `:root`, и на
`body` — с вариантами `[data-theme="light"]` / `[data-theme="dark"]`,
чтобы переключатель темы не возвращал светлый фон. **Сделано:**
`scripts/build-preview.py` пишет оба правила в шапку сборки.

## 2026-08-17 · Три дыры в контуре публикации Preview, найденные самопроверкой

Найдено при целевой проверке «может ли деплой задеть что-то помимо
одиннадцати Preview». Ни одна не проявилась бы как падение — все три
молчаливые.

**1. Страховка отключалась именно в узком режиме.** `verify-live-previews.py`
проверял боевой адрес только при полном прогоне: вызов `check_production()`
стоял под `if not args.only`. То есть при точечной публикации одного alias —
режим, где на живые адреса смотрят меньше всего — доказательство «боевой не
изменился» не выполнялось вовсе. Исправлено: проверка боевого адреса
безусловна. `LIVE-PREVIEW-READBACK` поднят до `1.1.0`.

**2. Значение из формы запуска подставлялось прямо в shell.** Шаг
`Live readback` писал `${{ inputs.only }}` внутрь `run:`. GitHub подставляет
выражение в текст скрипта **до** запуска shell, поэтому значение вида
`x"; команда; "` выполнилось бы как команда на раннере, где в том же job
уже использовался токен Cloudflare. Запускать workflow могут только люди с
write-доступом, так что это не публичный вектор, но шаг `Deploy previews`
рядом уже делал правильно — через `env`. Исправлено одинаково.

**3. Боевая ветка предполагалась, а не спрашивалась.** `deploy-previews.sh`
исходит из того, что production branch проекта — `main`, и поэтому ни один из
alias в него не попадёт. Проверки этого не было: если бы production branch
проекта оказался равен любому из одиннадцати alias, публикация Preview
уехала бы на боевой адрес молча. `deploy-pages.ps1` для боевого деплоя
спрашивает `production_branch` у API — здесь та же дисциплина не применялась.
Исправлено: шаг `Check token scope` читает `production_branch` из API и
останавливает запуск при совпадении с любым alias.

**Проверено.** Guard прогнан на двух сценариях: `production_branch = main`
проходит, `production_branch = final-dev` останавливает с exit 1. YAML
разобран, вложенный heredoc после дедента корректен. Локальные гейты после
правок: `verify-client-copy` PASS, `verify-client-previews` PASS 11/11,
`verify-lead-hook` PASS, unit-тесты `12/12`.

**Не проверено.** Реальное значение `production_branch` у проекта
`gambarian-landing` — на это нужен токен, которого в облачной сессии нет.
Проверку выполнит сам workflow при первом запуске.

**Урок.** Опасные места — не там, где код падает, а там, где страховка
выключена условием. Проверять не только «работает ли защита», но и «при каких
входах она не запускается».
